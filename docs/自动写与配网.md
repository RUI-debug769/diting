# 自动写 与 给板子设 WiFi

这两个功能的共同点：**手机是唯一的入口**，板子不需要按钮、不需要串口。

---

## 一、每天到点自动写

### 怎么用

设置页 → 「自动写」→ 点那个「关」，打一个时间（比如 `23:00`）→ 好。
想关掉就再点一次，按对话框里的「关掉」。

### 它是怎么跑的

| 环节 | 实现 | 文件 |
| --- | --- | --- |
| 排闹钟 | `AlarmManager.setExactAndAllowWhileIdle(RTC_WAKEUP, …)`，到点拉起 receiver | `android/.../AutoWrite.java` |
| 到点干活 | `goAsync()` 借时间 → 读当天事件 → 调模型 → 存盘 → 发通知 → 排下一天 | `android/.../AutoWriteReceiver.java` |
| 开机重排 | `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED` 各排一次 | `android/.../BootReceiver.java` |
| 权限 | `SCHEDULE_EXACT_ALARM`、`USE_EXACT_ALARM`、`RECEIVE_BOOT_COMPLETED`、`POST_NOTIFICATIONS` | `AndroidManifest.xml` |

为什么不用 `Handler`：Handler 只在 App 进程活着时有效，手机一锁屏被系统杀掉就永远不写。闹钟是系统级的，进程没了也能拉起来。

写完会发一条通知（「今天的话写好了，N 条」）；模型连不上就走本地兜底，通知里写「模型没连上，用了兜底」。

### 实测

把时间设成 `19:39`（当时 19:36），19:39:02 系统投递了这条 alarm：

```
D AlarmManager: mPendingIntent -> PendingIntent{… com.diting.app broadcastIntent}
```

随后右栏整列被填上、顶栏句子数从 25 涨到 31，第二天 19:39 的 alarm 也自动排好了（`origWhen` 指向次日）。

## 二、给板子设 WiFi

两条路，覆盖「板子已经在网」和「板子还没网」两种情况。

### 路 A：板子已经在网上（在线改）

设置页 →「板子的 WiFi」→ 填名字、密码 →「发给板子」。

```
App ──19002──► 云端 ──板子那条 TCP──► 板子
                 │                        │
                 └─ ack: 发给板子了        └─ 存 KV → 重启 → 连新网
```

云端那侧是 `_control()` 里的 `wifi` 分支，把 `{"cmd":"wifi","ssid":…,"pswd":…}` 原样转给板子；板子 `__poll_cmd()`（`tal_net_select` 非阻塞看一眼有没有数据）收到后 `diting_wifi_apply()` 存 KV，`tal_system_reset()` 重启，开机 `__wifi_load()` 从 KV 读出来连。

**连不上会自动退回上一组**（你选的口径）：板子每 2 秒重试一次，连续 45 次（约 90 秒）还没连上，就把 KV 里记着的「上一次连通过的那组」换回来再重启。所以填错了密码不会把板子变砖。

### 路 B：板子还没有网（首次 / 换地方）

两种情况会进配网模式：

1. 板子 KV 里一组 WiFi 都没有（新板子）；
2. 你在 App 里点了「让板子重新配网」——云端 `reprovision` 命令让板子清掉凭据、立一个「下次先配网」的旗子，然后重启。

进去之后：

```
板子开热点  Diting-Setup / diting1234   （192.168.4.1:19004）
手机连上这个热点
App 里填好名字、密码 →「发给板子」
  ├─ 先试云端：连不上（此时手机没网）→ 自动改连 192.168.4.1:19004
  └─ 板子收到 → 存 KV → 回 {"ok":true} → 重启 → 连你填的那个网络
```

App 的发送逻辑在 `SettingsActivity.sendWifi()`：先走云端，失败就把同一个 JSON 发给 `192.168.4.1:19004`——所以不管板子在不在线，按钮都是同一个。

### 实测

```
19:50:33 INFO App 让板子换成 WiFi「Murdo」
19:50:34 INFO 板子日记：收到新 WiFi Murdo，重启
19:50:39 INFO 板子接入 ('<公网地址>', 19019)
19:50:39 INFO 板子日记：连上了 board=0 audio_init=0 wake=0 片数=104 字节=0
```

从下发到重新连上，5 秒。

## 四、真机结论（2026-11-05 20:20，重要）

**定时自动写：完成，真机验证通过。** 到点自己写、写完整列回填、次日闹钟自动重排。

**给板子设 WiFi：只验证到「板子收到了」。**

- 已验证：设置页 → 云端 → 板子这条链路是通的，日志能同时看到
  `App 让板子换成 WiFi「Murdo」`、`板子日记：收到新 WiFi …，重启`、5 秒后 `板子接入`。
- **未验证 / 出问题**：把 SSID 换成一个**不存在**的网络（`NoSuchNet`）做回退测试，板子重启后再没回来，
  「90 秒退回上一组」没有生效，日志停在 `收到新 WiFi Murdo，重启`。板子自此 20 多分钟没再上过线，
  重新烧录（同版本）也没救回来。

排查到的事实：

1. KV **是能写进去的**——`NoSuchNet` 跨过一次重烧仍然生效，说明问题不在存储，在「回不去」。
2. 回退逻辑没触发：`__fallback_wifi()` 只在发送线程的空闲分支里跑，而板子连不上时那条路径的时序/条件
   还没被证实（串口读不到日志，只能靠网络自诊断，而自诊断又需要先连上——鸡生蛋）。
3. 结论：**这条功能现在有把板子锁死的风险**，在用起来之前不能算完成。

**最终处置（20:58）：固件里这条 KV 路已经整条关掉**——`__wifi_load()` 只认烧进去的
`DITING_WIFI_SSID`，`wifi` / `reprovision` 两条命令收到也只记一句「暂时关着」，
不再写 KV、不再重启。App 界面保留（带确认框），但点了不会生效。

原因：20:10 之后连烧四版固件、三次断电重插，板子都没再上过线；而这块板子的两个串口
（`/dev/ttyACM0` / `ttyACM1`）在 115200～2000000 各波特率下**读不到任何字节**，
没有日志就没法判断是「没跑起来」还是「跑起来但连不上」，继续盲改只是消耗你的时间。

**所以现在的处置：**

- App 里点「发给板子」会先弹一个确认框，写明「填错会掉线，得重新烧录恢复」；
- 该功能标记为 **实验性**，演示时不要用它改网；
- 下一步要先解决「看不见板子日志」这件事（串口 `ACM1` 各波特率都读不到可读输出），
  否则任何凭据/网络类 bug 都只能靠猜。

## 五、已知限制（更新）

- 配网模式下不推流；配网超时 5 分钟。
- 手机连 `Diting-Setup` 期间没有互联网。
- **改 WiFi 有锁死风险**（见上）。

## 附：早前记录的已知限制

- **配网模式下不推流**：板子此时是热点，不是客户端，录下来的声音也没人收——本来也不该记。
- **配网超时 5 分钟**：超时后板子按「没配成功」继续跑（有旧凭据就用旧的）。
- 手机连 `Diting-Setup` 的那几十秒**没有互联网**，这是必然的；配完板子会重连，手机切回原本的网络即可。
- 固件里的编译期默认 WiFi 仍然保留，作为「KV 里什么都没有」时的兜底；点过「重新配网」之后，旗子会让它以配网优先，不会偷偷连回默认那组。
