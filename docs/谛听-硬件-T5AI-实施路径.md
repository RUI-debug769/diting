## 0. 结论先行（三句话）

1. **你不是从零开始。** 仓库里五块拼图全有现成参考：LVGL 屏（`apps/shardcard`，你自己跑的）、表情脸（`apps/tuya.ai/your_desk_emoji`）、板载音频（`boards/T5AI/TUYA_T5AI_BOARD/tuya_t5ai_board.c:45` 已注册 16k/16bit/单声道 ADC 通路 + AEC）、TCP（`examples/protocols/tcp_client`）、BLE（`examples/ble/ble_peripher`）。今晚 1 小时该做的是**把"已有"验证成"可用"**，不是写新东西。
2. **最大的未知不是屏，是那颗咪头是否存在。** 主办方物料清单"没有麦克风器件" ≠ 板子上没有咪头——T5AI-BOARD 是语音 AI 参考设计，Kconfig 默认 `select ENABLE_AUDIO_CODECS`、代码里配了 16K 单声道输入和喇叭使能脚。今晚先花 10 分钟物理确认，再花 40 分钟用电平条证伪/证实。
3. **ESP32-S3 是个陷阱，而且是钱以外的陷阱。** 480×320 的屏 + GT1151 触摸是长在 T5AI 板上的；换主控＝同时失去屏、失去已验证的烧录链路、再花 50 元买不到屏。所以"切 S3"的真正闸门不是"T5 打不通 I2S"，而是"**这块板连 TCP/BLE 都跑不起来**"——概率极低。音频打不通时正确的降级是**换音频入口**（套件声音传感器 → 手机当麦），不是换主控。

## 2. 今晚 60 分钟（P0，最高优先级）

目标不是"做个脸"，是**用最小代价把"音频通路是否存在"这个问题一次性问死**，顺带证明屏+LVGL+音频能在同一个循环里共存。

### 0–10 min｜物理勘察（拍照存档，别跳过）
- 找咪头：板上找 **Ø4–6mm 圆形金属壳小件**，常见在屏排线附近；再找小喇叭（圆形/方形带孔）。
- 记丝印：主控模组型号、屏排线座子附近丝印、有没有 `MIC`/`SPK` 丝印。
- 摸一下是否有 **GT1151 触摸排线**（屏同时出两块 FPC）。
- 判据：**找到咪头 → 走 A 分支；找不到但有空焊盘/未贴件 → 走 B 分支（套件声音传感器）；完全没音频焊盘 → 走 C 分支（手机当麦）。**

### 10–25 min｜基线回归（先证明"没坏"再动手）
```bash
cd $TUYAOPEN
source export.sh
cd apps/shardcard && python3 ../../tos.py build      # 用 .build 缓存，增量很快
python3 ../../tos.py flash                            # 端口按实际改
```
- 判据：屏亮、横划翻卡动作和昨天一致。**这一步不过，今晚停止一切新功能**，先修工具链。

### 25–50 min｜"电平条"实验（核心）
在 `apps/shardcard` 上加 ~40 行（新文件 `src/sc_audio_probe.c`）：

```c
#include "tdl_audio_manage.h"
static TDL_AUDIO_HANDLE_T s_h;

static void mic_cb(TDL_AUDIO_FRAME_FORMAT_E fmt, TDL_AUDIO_STATUS_E st,
                   uint8_t *data, uint32_t len)
{
    int16_t *pcm = (int16_t *)data;
    uint32_t n = len / 2;
    int64_t acc = 0;
    for (uint32_t i = 0; i < n; i++) acc += (int32_t)pcm[i] * pcm[i];
    uint32_t rms = (uint32_t)sqrtf((float)(acc / (n ? n : 1)));
    /* 10ms 一帧：rms 存全局，UI 定时器读它画条 */
    g_rms = rms;
}

void sc_audio_probe_start(void)
{
    if (tdl_audio_find("audio", &s_h) != OPRT_OK) { PR_ERR("no codec"); return; }
    if (tdl_audio_open(s_h, mic_cb)  != OPRT_OK) { PR_ERR("open fail"); return; }
    /* 每 100ms 打印一次 dB，串口肉眼可见 */
}
```
UI 侧：`lv_timer` 每 33ms 读 `g_rms`，改一个 `lv_bar` 的值（条宽 400px 就够）。

- **通过判据（全满足）**：
  1. 串口 10 次/秒打印的 rms 值，**安静时 < 200、正常说话时 > 1500**（约 17dB 差，够做端点检测）；
  2. 屏上电平条随说话跳动，延迟 < 300ms；
  3. 连续跑 5 分钟不掉帧、不死机。
- **失败判据与动作**：
  - `tdl_audio_find` 返回非 `OPRT_OK` → codec 未注册：查 `CONFIG_ENABLE_AUDIO_CODECS` 是否被 `app_default.config` 关掉；仍失败 → **B/C 分支**。
  - rms 恒为 0 且说话无变化 → **无咪头 / 咪头虚焊 / 走错通道** → 先改 `cfg.ai_chn = TKL_AI_1` 再试一次（10 分钟），仍为 0 → **B/C 分支**。
  - rms 只在**敲桌子/摸板子**时跳 → 结构传声（板子把振动当声音）→ 加海绵垫/双面胶减震，并接受"只能做粗 VAD"的定位。
  - 屏掉帧/花屏 → 全屏重绘了。见 §3 的局部刷新规则。

## 3. ① 屏上那张脸：5 个状态与刷新预算

### 3.1 先算一笔账（决定架构的那笔）
- 全屏 = 480×320×2B = **307 KB/帧**。SPI 按 40 MHz 估 ≈ 61 ms/帧 → **全屏刷新只有 16 fps**，且会把 CPU 吃满。
- 因此：**脸只允许局部刷新**。眼睛区 160×80 = 25.6 KB ≈ 5 ms，嘴巴区 120×40 = 9.6 KB ≈ 2 ms → 60 fps 可行。
- 规则：`lv_obj_invalidate_area()` 只标脏区；背景纸纹/边框**只在状态切换时**重画一次，不做每帧动画。
- `CONFIG_LVGL_COLOR_DEPTH=32` 且开了双缓冲 → 帧缓冲 480×320×4 = **614 KB**，这块已经在跑（shardcard 证明了 PSRAM 够），别再加第三个 buffer。

### 3.2 五状态表（直接抄进 `enum liuer_state`）

| # | 状态 | 触发源 | 视觉（局部刷新的那几个量） | 动效 |
|---|---|---|---|---|
| 0 | `IDLE_BREATH` 呼吸 | 默认/超时 | 眼半闭（眼高 40%），瞳孔居中 | 整体 scale 0.98↔1.02，0.2 Hz 正弦 |
| 1 | `LISTENING` 在听 | 电平超阈值 / 手机 `EV_LISTEN` | 眼全开，瞳孔微放大，嘴闭合 | 瞳孔随 rms 左右微移；外圈一根 3px 弧随 rms 伸长 |
| 2 | `NOT_OWNER` 非本人 | 手机 `EV_STANGER`（声纹在手机侧判） | 眼眯成两条缝，单侧眉抬高 6px，色温转冷（背景 #F4F1EA→#E8ECF2） | 一次 120ms 的"眨眼皱眉"，然后静止 |
| 3 | `DENIED` 被否定 | 手机 `EV_DENIED`（用户点了"这不是我说的"） | 眼向下看（瞳孔 y+8），嘴抿成一条短线 | 整体缩到 0.94 再回弹 300ms，右上角一个 "×" 淡出 |
| 4 | `WRITING` 夜间书写 | 手机 `EV_WRITE` | 眼闭合（两条弧），面前一张纸 | 一条 2px 墨线从左到右自己长（每帧 +8px），速度 40px/s |

> 第 6 个状态建议白送：`DISCONNECT`（链路断）——眼变灰、呼吸停。评委拔掉手机时你不会尴尬，反而像"它在等"。

### 3.3 实现路线（二选一，按你手上的美术资源定）
- **A. 程序化（推荐，今晚就能动）**：`lv_obj` 画椭圆眼 + 弧眉 + 弧嘴，颜色/尺寸/位置全部由 `liuer_state` 驱动。零美术依赖，改一个数就换表情，**设计师给的是参数表不是图**。
- **B. 位图（美术已出图时）**：照 `apps/tuya.ai/your_desk_emoji` 的做法，每个表情一张 RGB565 C 数组，`lv_img_set_src()` 切换。代价：每张 480×320 图 ≈ 300 KB Flash，5 张就 1.5 MB——**只做眼睛/嘴的小图**（160×80 = 25 KB/张）才对。

### 3.4 一天内最小实验（11/6 上午）
- 实验：**一个按键循环切 5 个状态**，每个状态停 2 秒，屏幕录屏 30 秒。
- 通过判据：5 个状态肉眼可分；切换无残影；连续 10 分钟不崩；从按键到画面变化 < 100ms。
- 失败判据：切换后旧图形残留 → 脏区没清（`lv_obj_invalidate` 范围算错），改用整眼区重绘；帧率 < 20 fps → 有全屏重绘漏网，用 LVGL 的 `lv_refr_now` 前后打点定位。

## 4. ② 采集与粗端点检测

### 4.1 分两条 API 路线，别混用
- **路线 1（要原始 PCM，做上传）**：`tdl_audio_open()` + `mic_cb`，16K/16bit/单声道，10ms 一帧 = **320 B**。这是 spectrum_meter 已验证的用法。
- **路线 2（只要"有人说话"这个事件）**：`ai_audio_input_init()`，`vad_mode=AI_AUDIO_VAD_AUTO`，给 `vad_active_ms`（判为说话的持续时长）/`vad_off_ms`（静音多久算说完），回调直接吐"一段话"。
- **建议**：先用路线 2 把 VAD 跑通（半天），要上传时再换路线 1 自己算能量。**两条都基于同一路 16K 单声道 ADC。**

### 4.2 粗端点检测（自己写也就 20 行，可控）
```
帧 = 10ms 320B；rms 每帧算一次
门限 = 自适应：静默 3 秒内 rms 的滑动均值 × 3（或固定 1500，取大者）
进入说话：连续 3 帧 rms > 门限（30ms，防误触）
结束说话：连续 30 帧 rms < 门限（300ms，防吃字）
预录缓冲：进入说话前保留 300ms（ring buffer 里就有，别丢开头）
```
- 关键参数：**预录 300ms + 尾静音 300ms**。预录丢了，用户第一个字永远听不见——这是这类 demo 最常见的体验崩点。
- 环形缓冲：`16K×2B×10s = 320 KB` PSRAM，足够；用 `tuya_ringbuf`（spectrum_meter 用过）或自己写。

### 4.3 一天内最小实验
- 实验：串口打印 `[VAD] start @t / stop @t dur=1.8s`，对着板子说 5 句话、中途停顿 0.5 秒、再让旁边人说 2 句。
- 通过判据：5 句切成 5 段；**每段头部不丢字**（第一句的"我"要在）；停顿 0.5s 不被切断；背景说话不会把主说话人粘成一段（做不到也接受，声纹在手机侧）。
- 失败判据：一句话被切成 3 段以上 → `vad_off_ms` 太短，加到 500–800ms；环境噪声持续触发 → 门限改自适应，或把 `mic_volume` 降到 60 再试。

## 5. ③ 音频上手机：先算账，再选型

### 5.1 数字（15 秒，看完就有答案）
| 口径 | 码率 | 5 秒一句话 | 结论 |
|---|---|---|---|
| 16K/16bit/单声道 原始 | 32 KB/s | 160 KB | TCP 上 <0.2s；**BLE 上 8–16s** |
| 16K→8K + IMA ADPCM 4bit | 4 KB/s | 20 KB | TCP 上忽略不计；**BLE 上 1–2s（勉强）** |
| 全天连续录 | 115 MB/小时 | — | **设备端装不下，也不该装** |

**两个必须接受的结论：**
1. **设备不是"全天录音机"。** 一天 8 小时 = ~900 MB，T5 的 PSRAM 差两个数量级。所以"白天录音"这个动作在系统里必须由**手机持有存储**，设备只负责"把话递过去"。演示口径 = **5–10 分钟一场会话**（这完全够讲故事：一场会话就是"一段对话"，晚上把几段拼成一天）。
2. **BLE 不适合传原始音频。** 想用 BLE 就必须先做 ADPCM（两端都要写编解码 + 分包重组 + 重传），以你 10–12h 的总工时，这是把 60% 的预算押在链路上——而链路恰恰是最不该抢戏的部分。

### 5.2 选型判定
| 方案 | 工作量 | 现场风险 | 建议 |
|---|---|---|---|
| **手机开热点 + TCP**（`examples/protocols/tcp_client`） | **~2h** | 2.4G 拥挤、热点被系统省电杀 | **主线** |
| BLE GATT + ADPCM | ~6–8h | Android MTU/分包坑、吞吐不稳 | 只在 TCP 已通且有余力时做，且只做"状态通道" |
| USB（T5 作 UVC/UAC 或 CDC） | 高且不确定 | 手机 OTG + 驱动权限 | **不做**，直接毙掉 |

### 5.3 主线协议（照抄即可，4 字节头）
```
设备 → 手机（TCP，设备作 client 连手机热点网关:8888）
  帧头: magic(1)=0xA6 | type(1)=0x01 音频 | len(2, 小端) | payload
  payload: 16K/16bit/小端单声道 PCM，**按 20ms 一帧 = 640B** 连续发
  会话边界: type=0x02 会话开始（带 4B 时间戳），type=0x03 会话结束
手机 → 设备（同一连接，反向）
  8 字节定长: state(1) | param(1) | seq(2) | ts(4)
  state: 0 呼吸 / 1 在听 / 2 非本人 / 3 被否定 / 4 书写 / 5 断连
```
- 为什么 20ms 一帧：640B 正好塞进一个 TCP 段，也与 10ms 采音帧两两合并，不用拆包。
- 为什么定长下行：设备端解析成本≈0，不会因为 JSON 半包解析写崩。
- 心跳：手机每 1s 发一次 `state=当前`，设备 3s 收不到 → `DISCONNECT`。

### 5.4 一天内最小实验
- 实验：`tcp_client` 改 SSID/密码 → 连手机热点 → 每 100ms 发一个递增序号 + 那 320B 真实 PCM；手机端用 10 行 Python（`nc -l 8888 > dump.raw`）落盘，`aplay -f S16_LE -r 16000` 听。
- 通过判据：**能在电脑/手机上听出你说的话**（哪怕有噪声）；丢包率 < 1%；连续 10 分钟不断线。
- 失败判据：连不上 → 先 `ping` 网关（热点网关常见 `192.168.43.1` / `192.168.232.1`，按手机实际）；每隔 30–60s 断 → 手机热点省电策略，关掉"无设备时关闭热点"、锁屏保持；声音全是噪声 → 采样率对不上（手机端按 16K 解，设备若实际 8K 就会慢放）。

## 6. ④ 下行状态指令（这条最简单，别做复杂）

- 设备端一个 `liuer_set_state(uint8_t)`，内部只做：解析 8 字节 → 查表 → 触发 LVGL 切图 → 打日志。
- 断连处理：`DISCONNECT` 状态必须实现，**这是 demo 保命的**（评委拔手机、热点掉线时，脸不能僵死）。
- 触摸（GT1151 已可用）用它做一件事就够：**拍一下 → 本地立刻切 `DENIED` 并回一个 `EV_TAP` 给手机**。这一步 10 行代码，直接把"可交互"从"手机点按钮"升级成"拍它有反应"，对 `体验设计` 和 `完成度` 两维是白捡的分。

## 8. ESP32-S3 切换闸门（把话说死）

### 8.1 先算切换的真实成本
| 项 | 成本 |
|---|---|
| ESP32-S3 开发板 | 25–45 元（吃满 50 元预算） |
| **屏** | **480×320 + 触摸屏要另买，50 元买不到；不买＝没有脸＝项目没了** |
| 工具链 | 新 IDF 环境 + 新烧录链路，至少 3–4h（你只有 10–12h） |
| 已有增量 | shardcard 的 LVGL 代码可移植，但屏驱动/触摸驱动要重写 |

**结论：切换成本不是 50 元，是"屏 + 4 小时 + 一次 demo 崩盘风险"。**

### 8.2 真正该切的判据（三条同时成立才切）
1. 屏或触摸**在 T5 上完全不可用**（今晚基线回归失败且当天修不好）；
2. 或 `tdl_audio` + `ai_audio_input` + 套件声音传感器三条音频路径**全部**失败，且**你拒绝**"手机当麦"的叙事降级；
3. 且现场/淘宝能拿到 **带屏的** ESP32-S3 板（主办方物料里有"星火 2.7 寸屏开发板""微雪圆屏开发板"——**先去问主办方这两种板是不是 ESP32-S3 + 屏，如果是，切换成本≈0，这才是唯一值得切的理由**）。

### 8.3 时间闸门（到点必须做决定，不许拖）
- **11/6 20:00 前**：若屏上还没有"5 个状态可切换的脸" → 放弃一切链路自研，改为**手机录屏 + 设备只做脸**（脸永远能演）。
- **11/7 10:00 后**：禁止任何硬件改动。只允许改文案、补视频、修崩溃。

### 8.4 三条音频降级路线（比换主控便宜一万倍）
| 分支 | 做法 | 代价 | 叙事损失 |
|---|---|---|---|
| A | 板载咪头（若存在） | 0 元 | 无 |
| B | 38 种传感器套件里的**声音传感器模块**（驻极体+比较器，多数带 AO 模拟输出）→ 接 ADC，只做"有声/无声" | 0 元，1h | "它在听你"降级为"它感知到声音"——**但屏上电平条仍在，视觉证据不丢** |
| C | **手机当麦克风**，设备只做脸 + 收状态 | 0 元，0h | 声纹、方言识别全部名正言顺在手机侧；硬件只负责"神情" |

> C 不是失败方案，是**风险最低的方案**。你的评分里"技术实现"看的是"能不能跑"，"文化表达"看的是那张脸和日记——收音在哪一端，评委不会扒开外壳看。

## 10. 我替你做了的假设（你原话里没定，随时可推翻）

1. **演示口径按 5–10 分钟一场会话设计**，没按"真录一整天"（物理上设备存不下）。
2. **链路主线选 TCP**，BLE 只做状态通道或不作。
3. **声纹验证放在手机侧**——设备端没有现成的说话人识别推理栈（无模型、算力也吃紧），在 10 小时预算里自研不现实，这条必须在方案里让出去。
4. **脸用程序化 LVGL 画**（不依赖设计师出图），设计师给参数不给图，省掉一条关键路径。
5. 假设你有可用的 USB 数据线 + 能烧录的电脑（shardcard 已出包，应当成立）。

**需要你今晚确认的三件事**：① 板上到底有没有咪头/喇叭；② 你的手机开热点时能不能同时上网；③ 主办方的"星火 2.7 寸屏开发板"是不是 ESP32-S3（决定 S3 闸门是否真的零成本）。
