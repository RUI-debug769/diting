# 安卓修复补丁

改动只有两处，都落在现有方法里：`MainActivity.render()` 的计数口径、`DayView.onDraw()` 的竖线画法。没有新依赖，没有动布局和 `res/`，只碰这两个 java 文件。

先交代一件对不上的事：按当前这两个文件，两个缺陷其实都已经有半截代码在里面了。下面每条都先写清楚读到的是什么，补丁按文件的实际状态给，不按任务描述里的假想状态给。

## 和任务描述有出入的两点

**一、计数不是「没重算」。**

`MainActivity.java:422` 是文案没错，但 `sentences` 是 `render()` 的局部变量（`MainActivity.java:404`），每次进 `render()` 都从 0 重新数（`:406-419`）。三个改数据的地方都会调 `render()`：`addSpoken()` 末尾（`:259`）、`write()` 的 `onDone` 里（`:283`）、`denyLast()` 里（`:296`），启动时还有 `onCreate`（`:102`）。

不动的真实原因是口径：`:413-418` 只数 `。？！` 三个字符。`Asr.java:123-132` 把 `SpeechRecognizer` 的 `RESULTS_RECOGNITION` 第一条原样返回，不补标点；系统识别的中文结果基本不带句末标点。于是每加一句，`sentences` 确实重算了，结果还是 0——顶栏就停在「记下 0 句」。

**二、竖线不是没画，是画成了断的。**

`DayView.java:174` 确实有 `canvas.drawLine`，但它写在行循环里，每行只画 `row.top + 12dp` 到 `row.top + row.height - 12dp`。行高本身已经含了上下各 12dp 的 `vPad`（`DayView.java:120`），所以行与行之间空 24dp；首行上方、末行下方也各空 12dp。整页看是一条断续的短线。再叠上 `DIVIDE = #2A2622` 对 `BG = #12100E` 只有约 1.3:1 的对比度，屏幕上很容易被判成「没画」。

如果你手上的 APK 连断线都没有，那是装在 174 行之前的老版本，下面的补丁一样能用，它替换的就是这段。

### 3. 为什么这样改

- 口径选「原话句子数」，不选事件条数。`addSpoken()` 里 90 秒内的新话会并进上一条（`MainActivity.java:248-251`），一条事件可能是好几句，而文案写的就是「句」。按句子数还有个后手：现在系统识别不带标点，一段原话就按 1 句算，和按事件数结果一样；等 `Asr.java` 注释里说的 sherpa-onnx 那条路接上、识别结果带标点了，这个口径自动变准，不用再改一次。
- 切分用 `[。？！?!…]+`：中文句末标点、英文 `? !`、省略号都算句末；英文句点 `.` 故意不算，免得把「3.14」「a.m.」切碎。省略号算句末是个判断——口语里「……算了」多半是新起一句；不喜欢就把字符类里的 `…` 删掉，一个字符的事。
- 否定之后计数不变，这是有意的。`denyLast()` 只改 `its`（`MainActivity.java:292-294`），`mine` 没动，被否认的那句仍然是一条「记下」的记录。要改成「否认后减一」，把 `sentences += countSentences(e.mine);` 换成 `if (!e.denied) sentences += countSentences(e.mine);`。语义会从「记下几句」变成「还算数的几句」，我没有替你选这个。
- 顺手补了个空指针：旧循环直接读 `e.mine.length()`，`e.mine` 为 null 会崩（同方法 `:408` 那边已经防了 null，这里漏了）。helper 里判了 null。

### 1. 现状

`DayView.java:157` 算出了 `midX`，`:174` 只在每一行的文字高度那一段上画，行与行之间断开；整页没有一条从顶到底的线。

### 3. 为什么这样改

- 把画线从行循环里挪出来，循环走完画一次 `0 → getHeight()`。分段画的问题不是「看不出来」，是看得出是断的：每两行之间固定空 24dp，正好是一条横线的位置，视觉上像竖线被横线吃掉了。
- 用 `0` 和 `getHeight()`，不是内容高度。`DayView` 的注释里写的是「一条贯通的竖线」（`DayView.java:19`），贯通就该贯穿整页；内容只有两三行时线也照样到底，像账簿的竖栏。如果更想要「线只到内容底」，把 `getHeight()` 换成 `rows.get(rows.size() - 1).top + rows.get(rows.size() - 1).height`。
- `if (!rows.isEmpty())` 是留给空页的：一条记录都没有时不画孤线。
- 颜色、宽度都没改，还是 `linePaint` 的 `DIVIDE` 和 `Math.max(1f, dp(1f))`（`DayView.java:63-64`）。宽度用 dp(1)，和行间横线同一支笔，粗细一致；写死 1px 的话竖线会比横线细一档，反而看着不齐。在 420dpi 上 dp(1) ≈ 2.75px。
- `midX` 没动。它用的是浮点的半栏宽（`:157`），`build()` 里排版用的是整数 `colW`（`:94`），两者最多差 0.5px，肉眼看不出来。要让线严格落在两栏正中，可以把 157 行换成：

```java
int colW = (getWidth() - pad * 2 - gap * 2 - 1) / 2;
float midX = pad + colW + gap + 0.5f;
```

这是洁癖，不是修复，所以没放进补丁。

## 2026-11-05 19:25 「说了话但 App 没记录」的两个原因

**原因一（云端）：声纹阈值卡太死。** 同一个人短句只测出 0.478 / 0.586，阈值是 0.62 → 一律判成「别人」。实测分布：本人 0.48–0.73，陌生人 0.0–0.32，阈值改成 **0.48**（`diting_cloud.py` 的 `--threshold` 默认值），重部署后 19:22:50 那句 `score=0.696 accepted=true`。

**原因二（App，更隐蔽）：时间线根本滚不动。** `day` 之前是用 `height=0, weight=1` 加的，`DayView.onMeasure` 在 EXACTLY 模式下把高度钉成屏幕高，行一多，**新行直接被画到可见区外**——数据其实进了 `events`、`记下 N 句` 也在涨，但屏幕上永远停在第 6、7 行。修法：
- `day` 外面包一层 `ScrollView`（`fillViewport=true`），`day` 用 `WRAP_CONTENT`；
- `render()` 末尾 `scroller.post { fullScroll(FOCUS_DOWN) }`，新行自动滚到可见处。

验证：`记下 25 句`，最上面一行就是最新那句「喂喂喂，你好，我是薛瑞…」（截图 `out/手机-时间线可滚动-2026-11-05.png`）。
