# 挂坠固件：把声音推上云

> 位置：`~/tuya-ws/TuyaOpen/apps/diting/`（TuyaOpen 工作区里新建的工程）
> 产物：`firmware/diting_QIO_0.1.0.bin`（2.4M，另有 UA/UG 两种打包变体）

## 它做什么

```
T5AI 麦克风 → ai_audio_input（手动 VAD，一直开着）→ 40ms 一片
   → 队列（最多 50 片，约 2 秒）→ 发送线程 → TCP <你的服务器>:19001
```

帧格式和手机端 `NetRx.java`、云端 `diting_cloud.py` 完全一致：**4 字节小端长度 + PCM16k/16bit/单声道**。

板子这边不识别、不存声纹——1.7G 的云主机跑 ONNX 比板子划算，板子只负责把声音原样送到。
断了会自动重连，队列满了丢最旧的片，**绝不阻塞麦克风线程**。

## 关键实现（都在 `apps/diting/src/diting_main.c`）

- `ai_audio_input_init()` 用 `AI_AUDIO_VAD_MANUAL` + `slice_ms = 40`，然后
  **必须 `ai_audio_input_wakeup_set(true)`**——看源码 `ai_audio_input.c:177`，`__record_task`
  在 `!wakeup_flag` 时直接空转，不调这一句就一个字节都不会回调。
- 麦克风回调里只 `Malloc + memcpy + tal_queue_post`，网络全在发送线程里做。
- 发送线程 `tal_net_socket_create(PROTOCOL_TCP)` → `tal_net_connect` → `tal_net_send`，
  失败就关掉重连（退避 2 秒）。
- 入口是 `tuya_app_main()`（SDK 要的符号），真正的初始化丢进自己的线程，入口线程立刻返回。

## 烧之前必须改的两处

`apps/diting/src/diting_main.c` 顶部：

```c
#define DITING_WIFI_SSID "your-ssid"

#define DITING_CLOUD_IP   "<你的服务器>"

```

WiFi 没填对的话，板子会一直连不上，日志里能看到 `网络断了` 反复出现。

## 踩过的三个坑

1. `CONFIG_ENABLE_AI_COMPONENTS=y` 必须写进 `app_default.config`，否则 `ai_audio_input.h`
   根本不在 include 路径里（`src/ai_components/CMakeLists.txt` 整个被这个开关包住）。
2. `TUYA_CALL_ERR_LOG(...)` 宏要在作用域里有 `OPERATE_RET rt`，`-Werror` 下会直接编译失败
   （`tuya_error_code.h:820: error: 'rt' undeclared`）。
3. 应用入口是 `tuya_app_main()`，写成 `user_main()` 会链接失败：
   `undefined reference to 'tuya_app_main'`。

## 还没验证的

板子没插在电脑上（`/dev/ttyUSB*`、`/dev/ttyACM*` 都不存在），所以：
采样率/位深是否真是 16k/16bit/单声道、WiFi 连上后多久出第一片音频、长时间跑的稳定性——
**都要插上板子跑一次才算数**。云端侧已经用 `tools/sim_board.py` 按同样的帧格式验证过。

## 2026-11-05 19:12 排查记录：板子连上 WiFi 却一句话都推不上来

**现象**：对板子说话，App 一条都收不到；云日志里 `板子接入` 只有我自己用 `tools/sim_board.py` 推的 6 次。

**取证顺序**（从云端往回倒推）：
1. `grep -c 板子接入 /var/log/diting.log` = 6，全是我推的；ECS 上 `tcpdump -i any "tcp port 19001"` 120 秒 **0 包** → 板子根本没连云。
2. 手机热点 `ap0=10.x.x.x/24` 的客户端里找到了板子：`10.x.x.x`，MAC `d0:82:eb:xx:xx:xx`（OUI 查出来是 **Tuya Smart Inc.**），ping 通 115ms，但 `ss -tn` 里这个 IP **零 TCP 连接** → 板子活着、在局域网上，就是不往外发。
3. 板子 USB 通过 usbipd-win 挂进 WSL：`usbipd bind --busid 2-2`（要管理员）→ `usbipd attach --wsl --busid 2-2`，出现 `/dev/ttyACM0`（烧录口）和 `/dev/ttyACM1`（日志口，读出来是乱码，波特率没对上，暂时放弃串口）。

**两个真 bug（都已修）**：
- **`board_register_hardware()` 从来没被调用**。`tdl_audio_find()` 能查到节点，但 `node->tdd_hdl == NULL`，`tdl_audio_open()` 直接返回 `OPRT_INVALID_PARM(-2)` → `ai_audio_input_init()` 返回 -2，一个音频帧都没有。修法：`tuya_app_main` 里先 `board_register_hardware()`。修完 `board=0 audio_init=0 wake=0`，片数开始涨。
- **发送线程和麦克风只挂在 `EVENT_LINK_STATUS_CHG` 回调里**。这个事件在 WiFi 关联成功后不一定收得到，收不到就一条音频不推、也不连云端。修法：主流程里直接把发送线程和麦克风都起起来，连不上云端就每秒重试；发送线程空闲 1 秒也主动连一次（App 靠这条 TCP 判断「板子在线」）。

**为了让串口不必依赖，固件加了联网自诊断**：帧头长度字段写 `0x7FFFFFFF` 当暗号，后面跟「4 字节文本长度 + UTF-8」，云端解析后打 `板子日记：…`。启动/连上/空闲心跳各报一次 `board= audio_init= wake= 片数= 字节=`。这套东西在没有可用串口的场合非常值得留着。

**声纹那边的连带修复**：
- 手机麦克风录的声纹，拿去判板子麦克风的声音，分数常年卡在 0.6 附近（一会儿过一会儿不过）。新增「**用板子的麦克风录**」：App 发 `{"cmd":"enroll_board"}`，云端 30 秒内把板子切出来的第一段话直接当声纹（同一支麦克风，同人分数 0.7+）。
- 声纹从「一条向量」改成「**最多 3 条模板取最高分**」，旧的单条格式文件仍能读。
- 短于 1 秒的片段直接当噪声丢掉（0.6 秒那种判谁都只有 0.1，只会刷「不是你的声音」）；VAD 的 `min_silence` 从 0.45 调到 0.75，一句话不再被切碎。

**实测结果**（19:11）：`speaker=me score=0.728 text="今天下午我要去图书馆还书，顺便把上次借的两本看完。" duration=7.1 accepted=true`，App 左栏落行、`记下 17 句`。

## 2026-11-06 11:50 排查记录：连上了却一个字节都不发（根因是两个静默失败）

**现象**：板子 11:03 接上云端，传来一行 `连上了 board=0 audio_init=0 wake=0 片数=58 字节=0`，然后整整一上午再没有心跳、没有音频、也没有断开——TCP 连接一直挂在 `ESTAB`，云端一个字节都收不到。

**根因一：`tal_net_select` 的超时写 0 = 无限期阻塞。**

```c
/* 改前 */
tal_net_select(sg_sock_fd + 1, &set, NULL, NULL, 0)
```

`platform/T5AI/tuyaos/tuyaos_adapter/src/system/tkl_network.c:178-198` 里，`ms_timeout == 0` 会被翻成 `NULL timeval` 传给 `select`——那不是「立刻返回」，是「一直等到有数据」。发送线程连上云端后第一次进 `__poll_cmd` 就再也回不来：心跳不发、音频不发；2 秒后 50 片队列撑满，`tkl_queue_post(..., 0)` 在 IPC 上下文里要等 1 tick，把麦克风回调一起拖死。**片数冻在 58，就是这么来的。** 改成 20ms 即可。

**根因二：KV 里残留的「强制配网」旗子把每次开机都劫持进 AP 模式。**

串口日志（见下）第一屏就是：

```
[diting_main.c:178] WiFi 用编译进去的：Murdo
[diting_main.c:447] 没有 WiFi 凭据，进配网模式（热点 Diting-Setup / 密码 diting1234）
[diting_wifi.c:188] 切 AP 模式 rt=0
```

SSID 明明已经编译进固件，`diting_wifi_force_ap_pending()` 却读到了 KV 里的 `diting_force_ap=1`（早先配网流程 `diting_wifi_clear()` 留下的），于是板子每次上电都扎进 AP 模式等人来配网，**永远不会去连真正的 WiFi**。修法：`__diting_main` 里，编译进 SSID 时先把这个旗子撤掉（`diting_wifi_force_ap_clear()`）。

这两个 bug 的共同点是**上电后静默失败**——板子看起来「在工作」，实际上什么都没发。评审现场断电重来一次就会撞上。

**串口其实是能读的，之前读不出是方法不对**：

```bash
tyutool_cli monitor -p /dev/ttyACM1 -d t5ai --plain   # T5AI 的日志口是 460800
tyutool_cli reset  -p /dev/ttyACM0 -d t5ai            # DTR/RTS 复位，抓开机日志
```

`tos.py monitor` 在非交互环境会死在 `termios.tcgetattr`（要真 TTY）；自己用 pyserial 开 460800 也读不到东西，**必须用 tyutool 的 monitor**（它会先握手）。日志口是 `ACM1`，烧录口是 `ACM0`。

**另外加了「日志走 TCP」**：帧头 `0x7FFFFFFE` 当暗号，后面跟「4 字节长度 + UTF-8」，云端 `diting_cloud.py` 解析成 `板上日志：…`，不进 VAD、不占 `board_writer`。8KB 环形缓冲，抢不到锁就丢日志，绝不拖慢音频。没有串口的场合，这是唯一的可观测通道。

**验证结果**（11:51:13，真机、真热点、真说话）：

```json
{"speaker":"me","score":0.661,"text":"记一下明天下午3点和张老师开会。","duration":3.17,"accepted":true}
```

推流速率 31KB/s（16k × 16bit × 单声道 = 32000 B/s），40 秒推了 1250KB，稳定。
